# 02. Gherkin 기초 문법

> **이 글에서 배울 것**
> - `.feature` 파일의 구조와 위치
> - `Feature`, `Scenario`, `Given` / `When` / `Then` / `And` / `But` / `*`
> - 주석과 설명(Description)의 차이
> - 한국어 키워드 사용법
> - 초보자가 가장 많이 하는 실수
>
> **선수 지식**: [01. BDD와 Cucumber 핵심 개념](cucumber-concepts.md)

---

## 1. Gherkin이란?

**Gherkin**은 Cucumber가 이해하는 시나리오 작성 언어입니다. 프로그래밍 언어가 아니라
**몇 개의 키워드 + 자유로운 자연어 문장**으로 이루어져 있습니다.

- 줄의 맨 앞에 오는 **키워드**(`Feature:`, `Scenario:`, `Given` 등)만 문법으로 해석되고,
- 키워드 뒤의 나머지 문장은 사람이 자유롭게 씁니다.
- 파일 확장자는 `.feature`, 인코딩은 **UTF-8** 이어야 합니다.

이 프로젝트의 Feature 파일은 `src/test/resources/features/book_management.feature` 에 있습니다.
`src/test/resources/features` 폴더 아래의 `.feature` 파일은 모두 자동으로 실행 대상이 됩니다.

---

## 2. 가장 작은 Feature 파일 해부하기

이 프로젝트의 Feature 파일 일부를 한 줄씩 살펴봅시다.

```gherkin
Feature: 도서 관리                                    # (1) 기능 이름
  도서관 관리자로서                                   # (2) 설명 (Description)
  도서 목록을 관리하고 싶다
  그래서 이용자들이 도서를 쉽게 찾고 빌릴 수 있다

  Background:                                        # (3) 공통 전제 조건 (03장에서 자세히)
    Given 도서 데이터베이스가 초기화되어 있다

  Scenario: 존재하지 않는 ID로 조회하면 404를 반환한다  # (4) 시나리오 이름
    When ID 999999로 도서를 조회한다                  # (5) 행동
    Then 응답 상태 코드는 404이다                     # (6) 결과 검증
```

> 위 코드의 `# (1)` 같은 줄 끝 주석은 설명을 위해 붙인 것입니다.
> 실제 Gherkin에서는 **줄 끝 주석을 지원하지 않습니다** (주석은 한 줄 전체여야 합니다. 아래 7절 참고).

| 번호 | 요소 | 역할 |
|:---:|------|------|
| (1) | `Feature:` | 이 파일이 다루는 기능. 파일당 정확히 하나 |
| (2) | Description | `Feature:` 다음 줄부터 첫 키워드 전까지의 자유 텍스트. 실행에는 영향 없음 |
| (3) | `Background:` | 모든 Scenario 앞에서 매번 실행되는 Step 묶음 |
| (4) | `Scenario:` | 하나의 구체적인 예시 = 하나의 테스트 |
| (5) | `When` | 테스트하려는 행동 |
| (6) | `Then` | 기대하는 결과 |

## 3. Feature

```gherkin
Feature: <기능 이름>
  <설명: 여러 줄 자유롭게>

  Scenario: ...
```

- 파일의 첫 번째 키워드는 반드시 `Feature:` 입니다. (`# language:` 주석과 Tag는 그 위에 올 수 있음)
- 설명 부분은 보통 **사용자 스토리 형식**으로 씁니다. 형식이 강제되지는 않지만, 읽는 사람이 "왜 이 기능이 필요한지" 바로 알 수 있어 권장됩니다.

```
<역할>로서              As a <role>
<원하는 것>을 하고 싶다   I want <feature>
그래서 <얻는 가치>       So that <benefit>
```

---

## 4. Scenario

```gherkin
Scenario: 도서를 삭제한다
  Given "Test-Driven Development" 도서가 등록되어 있다
  When 해당 도서를 삭제한다
  Then 응답 상태 코드는 204이다
  And 해당 도서는 더 이상 조회되지 않는다
```

- **Scenario 하나 = 테스트 하나** 입니다. 리포트에도 Scenario 단위로 성공/실패가 표시됩니다.
- `Scenario:` 대신 동의어인 `Example:` 을 써도 됩니다. (BDD에서 시나리오는 곧 "예시"라는 의미)
- 이름은 **검증하려는 행동이 드러나게** 짓습니다.
  - 나쁜 예: `Scenario: 테스트1`, `Scenario: 삭제`
  - 좋은 예: `Scenario: 존재하지 않는 도서를 삭제하면 404를 반환한다`
- 각 Scenario는 **독립적**이어야 합니다. 다른 Scenario의 실행 결과에 기대면 안 됩니다.
  (실행 순서가 바뀌거나 하나만 골라 실행해도 통과해야 합니다.)

## 5. Step: Given / When / Then

Step은 Scenario를 구성하는 한 줄입니다. 세 가지 기본 키워드는 **AAA 패턴(Arrange-Act-Assert)** 과 정확히 대응합니다.

| 키워드 | 의미 | AAA 대응 | 이 프로젝트의 예 |
|--------|------|----------|------------------|
| `Given` | 행동 이전의 **상태(맥락)** 를 만든다 | Arrange | `Given "Refactoring" 도서가 등록되어 있다` |
| `When` | 검증하려는 **행동(사건)** 을 일으킨다 | Act | `When 해당 도서 가격을 29.99로 수정한다` |
| `Then` | 행동의 **결과(관찰 가능한 출력)** 를 확인한다 | Assert | `Then 수정된 도서 가격은 29.99이다` |

### Given — "이미 그런 상태다"

- 과거형 / 상태 표현으로 씁니다. ("등록되어 있다", "로그인한 상태다")
- 사용자의 행동이 아니라 **세계의 상태**를 설명합니다.
- 구현에서는 보통 DB에 직접 데이터를 넣거나 API를 호출해서 상태를 만듭니다.

### When — "이것을 한다"

- 현재형 / 동작 표현으로 씁니다. ("등록한다", "조회한다", "삭제한다")
- 원칙적으로 **Scenario 하나에 When은 하나**입니다. When이 여러 개라면 Scenario를 나눠야 할 신호입니다.

### Then — "그러면 이렇게 되어 있어야 한다"

- 결과를 **관찰 가능한 것**으로 표현합니다. (응답, 화면, 메시지, 조회 결과 등)
- 구현에서는 **반드시 검증(assertion)** 을 해야 합니다. 검증 없는 Then은 항상 통과하는 가짜 테스트입니다.

---

## 6. And, But, 그리고 `*`

같은 종류의 Step이 이어질 때 `Given`/`Then`을 반복하지 않고 `And`, `But`을 씁니다.

```gherkin
Scenario: 새 도서를 성공적으로 등록한다
  When 다음 정보로 도서를 등록한다:
    | title  | Clean Code       |
    | author | Robert C. Martin |
    | isbn   | 978-0132350884   |
    | price  | 35.99            |
    | stock  | 10               |
  Then 응답 상태 코드는 201이다
  And 등록된 도서 제목은 "Clean Code"이다
  And 등록된 도서 재고는 10권이다
```

- `And` : 앞 Step과 같은 종류를 이어갈 때 (위 예에서 두 `And`는 모두 `Then`의 연장)
- `But` : 앞 Step과 대비되는 내용을 이어갈 때 (예: `But 재고는 줄어들지 않는다`)
- `*` : 키워드 대신 쓸 수 있는 글머리표. 목록처럼 나열할 때 사용합니다.

```gherkin
Scenario: 도서 등록에 필요한 정보
  Given 관리자가 다음을 준비했다
  * 제목
  * 저자
  * ISBN
```

### 매우 중요: Cucumber는 키워드를 보지 않는다

Step Definition을 찾을 때 Cucumber는 **키워드(`Given`/`When`/`Then`/`And`/`But`)를 무시하고 문장 텍스트만** 비교합니다.

```gherkin
Given 응답 상태 코드는 200이다
Then 응답 상태 코드는 200이다
```

위 두 줄은 모두 `@Then("응답 상태 코드는 {int}이다")` 하나와 매칭됩니다.
따라서 Java 코드에서 `@Given`, `@When`, `@Then` 중 무엇을 붙이느냐는 **가독성을 위한 것**일 뿐 매칭에는 영향을 주지 않습니다.
그래도 의미에 맞는 어노테이션을 붙이는 것이 좋습니다.

## 7. 주석(Comment)과 설명(Description)

```gherkin
# 이것은 주석입니다. 리포트에 나오지 않습니다.
Feature: 도서 관리
  이것은 설명입니다. 리포트(HTML)에 함께 표시됩니다.

  # ──────────────────────────────
  # 도서 등록 시나리오
  # ──────────────────────────────

  Scenario: 새 도서를 성공적으로 등록한다
    시나리오에도 설명을 달 수 있습니다.
    When ...
```

| 구분 | 문법 | 리포트 노출 | 용도 |
|------|------|:---:|------|
| 주석 | `#`로 시작하는 **한 줄 전체** | X | 작성자 메모, 구역 구분 (이 프로젝트의 `# ────` 구분선) |
| 설명 | `Feature:`/`Scenario:`/`Rule:` 바로 다음 줄의 자유 텍스트 | O | 독자를 위한 배경 설명 |

- 주석은 반드시 줄의 처음(앞 공백 허용)에서 시작해야 합니다. `Then 결과 # 메모` 처럼 쓰면 `# 메모`까지 문장의 일부가 되어 매칭이 깨집니다.

---

## 8. 들여쓰기와 공백

- 들여쓰기는 **문법적 의미가 없습니다.** 하지만 관례적으로 2칸씩 들여씁니다.
  ```
  Feature:
    Scenario:          (2칸)
      Given ...        (4칸)
        | 표 |         (6칸)
  ```
- Step 문장 앞뒤 공백은 무시되지만, **문장 중간의 공백은 매칭에 그대로 반영**됩니다.
  `응답 상태 코드는  201이다`(공백 2개)는 `응답 상태 코드는 {int}이다`와 매칭되지 않습니다.
- 빈 줄은 자유롭게 넣어도 됩니다.

## 9. 한국어 키워드

파일 **첫 줄**에 `# language: ko`를 쓰면 키워드까지 한국어로 작성할 수 있습니다.

```gherkin
# language: ko
기능: 도서 관리
  도서관 관리자로서 도서 목록을 관리하고 싶다

  배경:
    조건 도서 데이터베이스가 초기화되어 있다

  시나리오: 존재하지 않는 ID로 조회하면 404를 반환한다
    만일 ID 999999로 도서를 조회한다
    그러면 응답 상태 코드는 404이다
```

| 영어 | 한국어 |
|------|--------|
| `Feature` | `기능` |
| `Background` | `배경` |
| `Scenario` | `시나리오` |
| `Scenario Outline` | `시나리오 개요` |
| `Examples` | `예` |
| `Given` | `조건`, `먼저` |
| `When` | `만일`, `만약` |
| `Then` | `그러면` |
| `And` | `그리고` |
| `But` | `하지만`, `단` |

주의할 점:

- `# language: ko`를 선언하면 그 파일에서는 **한국어 키워드만** 인식됩니다. `Feature:`와 `조건`을 섞어 쓸 수 없습니다.
- 앞서 말했듯 매칭은 문장 텍스트로만 하므로, Step Definition은 그대로 `@Given`/`@When`/`@Then`을 써도 됩니다.
- 이 프로젝트는 **영어 키워드 + 한국어 문장** 방식을 사용합니다. IDE 자동완성, 검색, 외부 도구 호환성 면에서 무난한 선택입니다.
  팀 내 비개발자가 영어 키워드를 낯설어한다면 한국어 키워드를 고려하세요. 어느 쪽이든 **프로젝트 안에서는 하나로 통일**하는 것이 중요합니다.

## 10. 초보자가 자주 하는 실수

| 실수 | 증상 | 바로잡기 |
|------|------|----------|
| `Feature`, `Scenario` 뒤 콜론(`:`) 누락 | 파싱 오류 | `Feature`, `Scenario`, `Background`, `Examples`, `Rule` 뒤에는 콜론이 필요합니다. `Given`/`When`/`Then` 뒤에는 콜론이 없습니다. |
| 한 파일에 `Feature:` 두 개 | 파싱 오류 | 파일당 Feature 하나. 나누고 싶으면 파일을 분리하거나 `Rule`을 사용합니다 (03장). |
| 문장 끝에 주석 | `Undefined step` | 주석은 한 줄 전체로만 씁니다. |
| Step 문장과 Step Definition의 글자가 미묘하게 다름 | `Undefined step` | 조사, 띄어쓰기, 콜론까지 정확히 일치해야 합니다. (`등록되어 있다` vs `등록되어있다`) |
| Then에서 검증하지 않음 | 항상 통과 | Then 메서드에는 반드시 `assertThat(...)`이 있어야 합니다. |
| 한 Scenario에 When-Then-When-Then | 실패 원인 파악이 어려움 | Scenario를 둘로 나눕니다. |

## 직접 해보기

아래 요구사항을 Gherkin Scenario로 작성해보세요. (Step Definition은 아직 작성하지 않아도 됩니다.)

> 관리자가 재고가 3권인 "Clean Architecture" 도서의 재고를 0권으로 수정하면, 수정은 성공하고 재고는 0권으로 조회된다.

<details>
<summary>예시 답안</summary>

```gherkin
Scenario: 도서 재고를 0권으로 수정할 수 있다
  Given 재고가 3권인 "Clean Architecture" 도서가 등록되어 있다
  When 해당 도서 재고를 0으로 수정한다
  Then 응답 상태 코드는 200이다
  And 수정된 도서 재고는 0권이다
```

이 Scenario에 쓰인 문장은 모두 `BookStepDefinitions`에 이미 구현되어 있습니다.
`book_management.feature`에 붙여넣고 `./gradlew test`를 실행하면 그대로 통과합니다.
기존 Step을 재사용하는 것만으로 새 테스트가 생기는 것이 Cucumber의 큰 장점입니다.
</details>
